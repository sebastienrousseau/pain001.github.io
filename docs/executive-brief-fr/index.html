Le problème#

Les banques rejettent les fichiers de paiement mal formés. Chaque rejet coûte un cycle de correction ; une correction qui manque l'heure limite coûte un jour de règlement. Les motifs de rejet sont connaissables à l'avance — donc évitables.

L'échéance#

14 novembre 2026, appliquée au niveau du réseau : les paiements transfrontaliers (CBPR+) portant des adresses entièrement non structurées seront rejetés, et le canal interbancaire MT101 hérité sera remplacé par pain.001 version 9 (ISO 20022). L'exposition se trouve dans vos données clients. Sources : SWIFT, citées intégralement sur pain001.com/2026-iso20022-migration-trends.

Ce que fait Pain001#

Une suite open source qui convertit les données existantes — tableurs, exports ERP, anciens fichiers SWIFT — en fichiers de paiement ISO 20022 prêts pour la banque, et prouve chaque fichier contre le référentiel officiel de la banque (XSD ISO 20022) avant soumission. Tout s'exécute sur votre propre infrastructure : aucun envoi, aucun cloud tiers, aucune télémétrie.

Ce que cela coûte#

Rien, à toute échelle, sous licences ouvertes (Apache-2.0 / MIT). Point de référence commercial : le SDK de traduction de SWIFT est affiché publiquement entre 10 000 et 30 000 € par an.

Les preuves#

Inventaire des dépendances publié (SBOM) · couverture de code de 100 % imposée en CI · chaîne d'approvisionnement notée indépendamment (OpenSSF Scorecard) · documentation accessible WCAG 2.2 AAA · politique de sécurité avec divulgation privée. Tout est vérifiable sur pain001.com.

La demande#

Faites exécuter la démo de 60 secondes par votre équipe d'ingénierie des paiements sur pain001.com/try — elle valide un lot d'exemple et le prouve contre le schéma officiel ISO 20022, dans le navigateur, sans rien téléverser. Si cela tient, l'installation prend quelques minutes.
