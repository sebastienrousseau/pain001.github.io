# pain001.com v0.0.5

Version 0.0.5 completes the release-engineering fix begun in v0.0.4. The site
itself is unchanged since v0.0.3; this release exists so that content reaches
a published release with its archive, checksums, SBOM and attestations intact.

Two separate faults stopped the release, one masking the other:

- **v0.0.3** failed with `SBOM file not found`. `actions/attest-sbom` expands
  globs in `subject-path` but not in `sbom-path`, so the pattern never
  resolved. Fixed in v0.0.4 by naming both paths in full.
- **v0.0.4** then failed with `Unsupported SBOM format`. The action detects
  CycloneDX with `bomFormat && serialNumber && specVersion`, and ssg's SBOM
  omits the optional `serialNumber`, so detection fell through to the error.

The fix:

- `scripts/sbom_serial.py` adds a `serialNumber` to the generated SBOM during
  the build, derived as a UUIDv5 over the site's base URL and version rather
  than generated randomly, so rebuilds of a version carry the same serial and
  this pass adds no nondeterminism of its own. The SBOM as a whole still
  varies between builds, because ssg stamps `metadata.timestamp` into it.

The script self-checks the exact condition the attestation action applies, so
a later change cannot quietly reintroduce an unpublishable SBOM. The complete
release workflow was exercised as a dry run before this tag was created.

Emitting `serialNumber` belongs in ssg's SBOM plugin; this keeps releases
publishable until that lands, and the script becomes a no-op once it does.

Tags are immutable, so v0.0.3 and v0.0.4 keep their tags and attestations
without published releases.
