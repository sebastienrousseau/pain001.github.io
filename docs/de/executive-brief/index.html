Das Problem#

Banken weisen fehlerhaft aufgebaute Zahlungsdateien zurück. Jede Ablehnung kostet einen Korrekturzyklus; eine Korrektur, die den Annahmeschluss des Tages verpasst, kostet einen Settlement-Tag. Die Ablehnungsgründe sind im Voraus erkennbar — und damit vermeidbar.

Der Termin#

14. November 2026, durchgesetzt auf Netzwerkebene: Grenzüberschreitende Zahlungen (CBPR+) mit vollständig unstrukturierten Adressen werden abgelehnt, und der alte Interbanken-Kanal MT101 wird zugunsten von ISO 20022 pain.001 Version 9 eingestellt. Das Risiko liegt in den Kundenstammdaten. Quellen: SWIFT, vollständig belegt unter pain001.com/2026-iso20022-migration-trends.

Was Pain001 tut#

Eine Open-Source-Suite, die vorhandene Daten — Tabellenkalkulationen, ERP-Exporte, alte SWIFT-Dateien — in bankfertige Zahlungsdateien nach ISO 20022 umwandelt und jede Datei vor der Einreichung gegen das offizielle Regelwerk der Bank (ISO 20022 XSD) nachweist. Sie läuft vollständig auf Ihrer eigenen Infrastruktur: kein Upload, keine Anbieter-Cloud, keine Telemetrie.

Was es kostet#

Nichts, in jedem Umfang, unter offenen Lizenzen (Apache-2.0 / MIT). Kommerzieller Referenzpunkt: Das Übersetzungs-SDK von SWIFT ist öffentlich mit 10.000–30.000 € pro Jahr gelistet.

Die Belege#

Veröffentlichtes Abhängigkeitsinventar (SBOM) · Code mit 100 % Branch-Coverage als CI-Gate · unabhängig bewertete Lieferkette (OpenSSF Scorecard) · nach WCAG 2.2 AAA barrierefreie Dokumentation · Sicherheitsrichtlinie mit vertraulicher Meldung. Alles überprüfbar auf pain001.com.

Die Bitte#

Lassen Sie Ihr Payments-Engineering-Team die 60-Sekunden-Demo unter pain001.com/try ausführen — sie validiert einen Beispielstapel und weist ihn gegen das offizielle Schema nach ISO 20022 nach, im Browser, ohne dass etwas hochgeladen wird. Hält das stand, dauert die Installationsanleitung nur Minuten.
